Conseil

Choisissez un langage que vous connaissez déjà. Le but du TP est le CI/CD, pas d'apprendre un nouveau langage. Si vous hésitez, Node.js + Express ou Python + Flask sont les choix les plus rapides.

Ce qu'il faut faire :

  • ✔ Créer un nouveau repository GitHub (public)
  • ✔ Le cloner sur votre machine
  • ✔ Initialiser votre projet avec le gestionnaire de dépendances de votre langage
  • ✔ Installer votre framework web, votre librairie de test, et votre linter
  • ✔ Créer un fichier .gitignore adapté à votre langage
  • ✔ Configurer les scripts/commandes pour : démarrer le serveur, lancer les tests, lancer le linter
  • ✔ Premier commit : chore: initialiser le projet [votre techno]

4

Implémenter les endpoints de l'API

7 routes à créer. Lisez bien les spécifications.

Votre API doit exposer les endpoints suivants. Tous doivent renvoyer du JSON.

GET/students

Objectif : Récupérer la liste de tous les étudiants. → Code 200 + tableau JSON

GET/students/:id

Objectif : Récupérer un étudiant par son ID.

  • • 200 + l'objet étudiant si trouvé
  • • 404 si l'ID n'existe pas
  • • 400 si l'ID n'est pas un nombre valide
POST/students

Objectif : Créer un nouvel étudiant.

Validations à implémenter :

  • • Tous les champs sont obligatoires → sinon 400
  • • firstName et lastName : min 2 caractères → sinon 400
  • • email : format valide → sinon 400
  • • email : doit être unique → sinon 409
  • • grade : entre 0 et 20 → sinon 400
  • • field : une des 4 valeurs autorisées → sinon 400

Succès : 201 + l'objet créé avec son ID auto-généré

PUT/students/:id

Objectif : Modifier un étudiant existant.

  • • 200 + l'objet mis à jour si succès
  • • 404 si l'ID n'existe pas
  • • 400 si données invalides (mêmes règles que POST)
  • • 409 si email déjà pris par un autre étudiant
DELETE/students/:id

200 + message de confirmation si supprimé, 404 si l'ID n'existe pas

GET/students/stats

Objectif : Statistiques sur les étudiants. Code 200 avec :

  • • totalStudents : nombre total
  • • averageGrade : moyenne des notes (arrondie à 2 décimales)
  • • studentsByField : nombre par filière
  • • bestStudent : meilleure note
GET/students/search?q=...

200 + étudiants dont nom/prénom contient le terme (insensible à la casse). 400 si paramètre q absent/vide.

Attention à l'ordre des routes !

/students/stats et /students/search doivent être déclarées avant /students/:id.

Commits suggérés :

  • feat(api): ajouter les routes GET pour les étudiants
  • feat(api): ajouter la route POST avec validation
  • feat(api): ajouter les routes PUT et DELETE
  • feat(api): ajouter les routes stats et search

Écrire les tests automatisés

Minimum 15 tests. C'est le coeur du CI/CD.

Pourquoi les tests ?

Le pipeline exécute vos tests à chaque push. S'ils passent = code OK. S'ils échouent = push signalé. Les tests sont la garantie de qualité du CI/CD.

Rôle des tests dans le pipeline

Les 15 tests minimum à écrire

GET Tests de lecture (5 tests)

  • 1. GET /students doit renvoyer 200 et un tableau
  • 2. GET /students doit renvoyer tous les étudiants initiaux
  • 3. GET /students/:id valide doit renvoyer l'étudiant correspondant
  • 4. GET /students/:id inexistant doit renvoyer 404
  • 5. GET /students/:id invalide (ex: "abc") doit renvoyer 400

POST Tests de création (4 tests)

  • 6. POST avec données valides doit renvoyer 201 + l'étudiant avec un ID
  • 7. POST sans champ obligatoire doit renvoyer 400
  • 8. POST avec note invalide (ex: 25) doit renvoyer 400
  • 9. POST avec email déjà existant doit renvoyer 409

PUT Tests de modification (2 tests)

  • 10. PUT avec données valides doit renvoyer 200 + l'étudiant modifié
  • 11. PUT avec ID inexistant doit renvoyer 404

DELETE Tests de suppression (2 tests)

  • 12. DELETE avec ID valide doit renvoyer 200
  • 13. DELETE avec ID inexistant doit renvoyer 404

GET Tests stats & search (2 tests)

  • 14. GET /students/stats doit renvoyer totalStudents, averageGrade, studentsByField, bestStudent
  • 15. GET /students/search?q=... doit renvoyer les étudiants correspondants

Conseils :

  • • Réinitialisez les données avant chaque test pour qu'ils soient indépendants
  • • Vérifiez le code de statut ET le corps de la réponse
  • • Utilisez une librairie HTTP pour tester sans démarrer le serveur manuellement

Commits : test(api): ajouter les tests GET puis test(api): ajouter les tests POST, PUT, DELETE, stats, search

Configurer le linter

Qualité et cohérence du code.

Ce qu'il faut faire :

  • ✔ Installer le linter de votre langage
  • ✔ Créer un fichier de configuration avec des règles (pas de variables inutilisées, indentation cohérente, pas de console.log/print oubliés)
  • ✔ Ajouter une commande pour lancer le linter
  • ✔ Corriger toutes les erreurs dans votre code existant

Le linter doit passer à 0 erreurs !

Dans le pipeline, la moindre erreur = pipeline rouge.

Commit : chore(lint): configurer le linter et corriger les erreurs

Push et vérifier le pipeline

Le moment de vérité !

  1. Poussez tout sur GitHub (commits Conventional Commits)
  2. Allez sur votre repo → onglet "Actions"
  3. Votre workflow doit apparaître en cours d'exécution
  4. Cliquez pour voir le détail de chaque étape
  5. Attendez le vert ✅

Pipeline rouge ?

Lisez les logs d'erreur sur GitHub, corrigez en local, poussez un nouveau commit. C'est le cycle normal du CI/CD !

  2. Introduisez un bug (changer un code de statut, casser une validation...)
  3. Commit + push : test: introduire un bug intentionnel pour démontrer le CI
  4. Constatez le pipeline rouge (capture d'écran !)
  5. Corrigez + push : fix: corriger le bug intentionnel

Problèmes fréquents

❌ "Le pipeline ne se déclenche pas"

  • • Fichier dans .github/workflows/ci.yml (ce chemin exact)
  • • Indentation YAML (espaces, pas tabs)
  • • Noms de branches dans le trigger

❌ "Tests OK en local, KO dans le CI"

  • • Dépendances dans le fichier de config (pas installées globalement)
  • • Pas de chemins en dur
  • • Serveur ne reste pas en écoute après les tests

❌ "Erreur YAML"

  • • YAML est très strict sur les espaces
  • • Validateur YAML en ligne
  • • Jamais de tabulations

❌ "/students/stats interprété comme /students/:id"

Déclarez /students/stats et /students/search avant /students/:id
